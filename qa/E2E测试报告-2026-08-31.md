## 二、缺陷清单（按严重程度）

### 高

**H1 · 支付回调缺幂等：同一订单并发支付全部成功，产生重复账单与重复消息**
- 问题描述：并发 N 次支付同一订单，N 次全部返回成功；产生 N 条 `pay_bill`、N 条重复"支付成功"消息，核销码被后写者覆盖（前 N-1 个响应返回的核销码与订单最终核销码不一致）。
- 所在位置：`backend/src/main/java/com/thrombosis/service/OrderService.java:119-131`（`mockPayCallback`：selectById 查状态 → updateById，check-then-act 非原子；与已修复的 #4 核销竞态同款模式）。
- 复现/触发：对同一 pending_pay 订单并发调用 8 次 `POST /api/payment/mock-callback`。实测：成功 8 次、billRows=8、msgs=8。
- 预期正确行为：支付幂等——仅一次生效（带 `status='pending_pay'` 条件的原子更新，更新 0 行直接返回已支付结果），账单/消息/销量只在首次产生。微信官方回调语义要求幂等处理（重复投递是常态），该模式将被真实支付回调复用。
- 注：当前端点仅 dev 开放（`thrombosis.dev.mock.payment`），生产此路径关闭，故未评级为阻断。

### 中

**M1 · 支付销量自增丢更新**
- 问题描述：同套餐多订单并发支付，全部支付成功但销量远少于成功笔数。实测：12 笔订单 12 笔支付成功，销量 1832→1834（+2，应 +12）。
- 所在位置：`backend/src/main/java/com/thrombosis/service/OrderService.java:144-149`（selectById → setSalesCount(+1) → updateById，读-改-写非原子）。
- 复现/触发：并发支付同套餐的不同订单。
- 预期正确行为：`UPDATE package SET sales_count = sales_count + 1 WHERE id = ?` 数据库原子自增。

**M2 · 订单号碰撞导致下单偶发 500**
- 问题描述：`order_no` = TH + 秒级时间戳 + 3 位随机（每秒仅 1000 个槽位），同秒并发下单触发 `uk_order_no` 唯一键冲突 → 用户收到 500"服务异常，请稍后重试"。实测：60 笔同秒并发下单失败 1 笔，后端日志 `Duplicate entry 'TH20260831203235244' for key 'orders.uk_order_no'`。
- 所在位置：`backend/src/main/java/com/thrombosis/service/OrderService.java:198-201`（`genOrderNo`）。
- 复现/触发：同秒并发下单（并发用户/营销高峰；60 并发实测命中率 1/60）。
- 预期正确行为：更长的随机段/分布式序列；或捕获 DuplicateKey 自动重试生成，用户无感。

### 低

**L1 · 并发打卡败者返回 500**
- 问题描述：并发打卡同一时间点，唯一键 `uk_med_date` 保证数据正确（仅 1 条记录），但败者请求返回 500"服务异常，请稍后重试"。实测：6 并发 → 1 成功 / 5 失败（500）。
- 所在位置：`backend/src/main/java/com/thrombosis/service/MedicationService.java:82-99`（selectOne 判存 → insert 的 upsert 非原子，DuplicateKeyException 未捕获）。
- 预期正确行为：捕获重复键视为幂等成功（当天该时间点已打卡）。

**L2 · 会话与验证码机制的生产化局限（设计观察）**
- 问题描述：短信验证码无 TTL（发出后永久有效直到使用）；验证码与 registerTicket 存 JVM 内存（重启丢失、多实例不共享）；账号禁用后已签发 token 在有效期内（7 天）仍可访问。
- 所在位置：`AuthService`（codeStore/ticketStore 内存 Map）、`security/AuthInterceptor`（仅校验 JWT 不查用户状态）。
- 预期正确行为：生产化时验证码加 TTL + 限次校验、状态外置（Redis/DB）；禁用即时生效需拦截器校验用户状态或 token 黑名单。

| 缺陷 | 修复方式 | 复测结果 |
|---|---|---|
