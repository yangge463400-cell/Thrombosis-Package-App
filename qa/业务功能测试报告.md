首轮在 H2 上遇到的两处环境差异（**均为 H2 特性，非项目缺陷**），在 MySQL 上自然消失，已实证：

1. **索引名作用域**：`schema.sql` 中 `orders`/`test_result`/`medication`/`message` 四张表都定义了名为 `idx_user` 的索引。MySQL 索引名作用于**表内**（允许重名），H2 作用于**整个 schema**（不允许重名）→ H2 下后 3 张表建表失败，需 `qa/tmp/h2-fix.sql` 补丁重建。**MySQL 下 12 张表一次建成，证明 `schema.sql` 本身完全有效。**
2. **JSON 列 `setString` 二次编码**：用 `qa/tmp/JsonProbe.java` 实证——H2 下 `ps.setString(i, "[\"a.png\"]")` 读回是 `"[\"a.png\"]"`（二次编码），而 SQL `JSON_ARRAY('seed.png')` 读回是 `["seed.png"]`；这导致 H2 下"编辑套餐"必 500。**MySQL 下 `POST/PUT /api/admin/packages` 全部返回 `code=0`，套餐新增/编辑/上下架/列表均正常**，证明该路径无问题（H2 下已用补丁把相关列降为 VARCHAR 规避）。

#### 缺陷 1 · 任意登录用户可为他人订单支付，取得他人核销码

- **【所属模块/功能】** 支付 Payment / `POST /api/payment/mock-callback`
- **【缺陷描述】** 支付回调接口不校验订单归属。`OrderService.mockPayCallback(orderId)` 只按 `orderId` 查订单，未比对 `order.userId` 与当前登录用户，任何登录用户都能把任意订单（含他人订单）刷成"已支付"并拿到 6 位核销码。
- **【复现步骤】**
  1. 用户 A 登录取得 token
  2. `POST /api/payment/mock-callback`，Header 带 A 的 token，body `{"orderId": 3}`（订单 3 属 `user_id=1`）
  3. 观察返回
- **【预期结果】** 校验订单归属，非本人订单返回 403/404，拒绝支付
- **【实际结果】** `code=0` 调用成功，返回 `status=paid, verifyCode=668850`。攻击者可免费获取他人订单核销码到院检测；反向亦可把任意订单刷成已支付。真实微信支付回调若沿用同一 Service 方法，风险等价
- **【严重程度】** 严重
- **【关联代码位置】** `backend/src/main/java/com/thrombosis/controller/PaymentController.java:30-42`（未取 `UserContext`）；`service/OrderService.java:119-155`（`mockPayCallback` 未校验 `o.getUserId()`）

#### 缺陷 2 · 核销码二维码接口完全未鉴权，且订单 ID 可枚举

- **【所属模块/功能】** 订单 Order / `GET /api/orders/{id}/qrcode`
- **【缺陷描述】** 该接口被显式加入公开放行列表，任何人在不携带 token 的情况下，遍历递增的 orderId 即可批量下载全部用户的核销码 PNG。
- **【复现步骤】**
  1. 不携带任何 Authorization
  2. `GET http://localhost:8080/api/orders/1/qrcode`
  3. 把 `1` 依次换成 `2`、`3`、`4`…
- **【预期结果】** 需鉴权 + 校验订单归属（或改用签名短链）
- **【实际结果】** 返回 `HTTP 200`，`content-type: image/png`，成功取得 PNG 图片
- **【严重程度】** 严重
- **【关联代码位置】** `backend/src/main/java/com/thrombosis/config/WebMvcConfig.java:26`（公开放行）；`controller/OrderController.java:63-80`

#### 缺陷 3 · 微信登录 openid 被固定为常量，所有用户共用同一账号

- **【所属模块/功能】** 认证 Auth / `POST /api/auth/wechat-login`
- **【缺陷描述】** 未配置 `WX_APPID`/`WX_SECRET` 时，`resolveOpenid()` 直接返回 `openidPrefix + "stable"`，与传入的 code 无关。生产环境若漏配环境变量，所有微信用户都会映射到同一个账号，可互相看到订单、检测结果、用药方案。真实 `code2session` 代码已写好（仅靠环境变量切换），但回退策略是"静默共用账号"而非"拒绝服务"。
- **【复现步骤】**
  1. `POST /api/auth/wechat-login` body `{"code":"A"}`
  2. `POST /api/auth/wechat-login` body `{"code":"B"}`
  3. 比对两次返回的用户身份
- **【预期结果】** 不同 code 应映射到不同 openid；生产环境缺少凭据时应快速失败，不得回退为共用账号
- **【实际结果】** 两次返回同一身份分支（`isRegistered` 一致），无法区分用户
- **【严重程度】** 严重
- **【关联代码位置】** `backend/src/main/java/com/thrombosis/service/AuthService.java:145-151`

#### 缺陷 4 · 并发核销可重复写入多条核销记录（check-then-act 非原子）

- **【所属模块/功能】** 医护与核销 Verify / `POST /api/verify/confirm`
- **【缺陷描述】** `confirm()` 先 `selectOne` 判断状态再 `update`，两步之间无锁。并发请求可同时通过状态判断，重复写 `verify_record`、重复发站内消息，造成核销统计虚高与对账差异。
- **【复现步骤】**
  1. 下单（套餐任意 + 医院 1）并用 `/api/payment/mock-callback` 支付，取得核销码
  2. 用医护 token **并发 6 次** `POST /api/verify/confirm {"code":"<核销码>"}`
  3. 查 `GET /api/verify/records`，统计该订单的记录数
- **【预期结果】** 6 个并发请求中只有 1 次真正核销，`verify_record` 只新增 1 条
- **【实际结果】** **6 次全部成功，该订单核销记录从 0 条变成 6 条**（新增 6 条）
- **【严重程度】** 严重
- **【关联代码位置】** `backend/src/main/java/com/thrombosis/service/VerifyService.java:62-98`（无行锁/乐观锁）；`db/schema.sql:88-103`（`verify_record` 无 `uk(order_id)` 兜底）

#### 缺陷 6 · 医护工作台"待处理数"未按医院过滤，泄露全库数据

#### 缺陷 9 · 套餐列表全表加载后在内存中过滤/排序/分页

- **【所属模块/功能】** 套餐 Package / `GET /api/packages`

- **【严重程度】** 一般

#### 缺陷 10 · 分页参数 `page=0` 或负数导致 500

- **【所属模块/功能】** 套餐 Package / `GET /api/packages`
- **【缺陷描述】** 承上，内存分页计算 `from = Math.min((page-1)*pageSize, total)` 只兜了上界未兜下界。`page=0` 时 `from=-10`，随后 `subList(-10, 0)` 抛 `IndexOutOfBoundsException: fromIndex = -10` → 500。
- **【复现步骤】** `GET /api/packages?page=0&pageSize=10`（`page=-1` 同样复现）
- **【预期结果】** 返回第一页或参数错误 400
- **【实际结果】** `code=500 服务异常，请稍后重试`
- **【严重程度】** 一般
- **【关联代码位置】** `backend/src/main/java/com/thrombosis/service/PackageService.java:49-52`

#### 缺陷 11 · 请求体携带未定义字段返回 500 而非 400

- **【所属模块/功能】** 全局 / 所有接收 JSON 的接口
- **【缺陷描述】** 未关闭 Jackson 的 `FAIL_ON_UNKNOWN_PROPERTIES`，且 `GlobalExceptionHandler` 未处理 `HttpMessageNotReadableException`。字段拼写错误、前后端字段版本不一致、第三方对接多传字段，都会表现为"服务异常，请稍后重试"，排障困难。
- **【复现步骤】** `POST /api/orders`，body `{"packageId":1,"hospitalId":1,"unknownField":"x"}`
- **【预期结果】** 400 + 明确指出未知字段
- **【实际结果】** `code=500`
- **【严重程度】** 一般

#### 缺陷 12 · 订单状态机 `verified`（检测中）不可达

- **【所属模块/功能】** 医护与核销 Verify / 订单状态流转
- **【缺陷描述】** 规格文档、`schema.sql` 注释、小程序 `config.ORDER_STATUS` 都定义了 `paid → verified(检测中) → completed`，但 `VerifyService.confirm()` 直接从 `paid` 置为 `completed`（代码注释自述"核销即完成"）。"检测中"状态永不出现，用户端"检测中"文案永不展示。
- **【复现步骤】** 走完"下单 → 支付 → 医护核销"流程后查看订单 `status`
- **【预期结果】** 核销后进入 `verified`（检测中），医护出具结果后转 `completed`
- **【实际结果】** 核销后直接为 `completed`，`verified` 不可达
- **【严重程度】** 一般
- **【关联代码位置】** `service/VerifyService.java:80-81`；`db/schema.sql:73`；`miniapp/config/index.js:30`

#### 缺陷 13 · 开发态微信登录无法登录到示例账号，README 演示流程走不通

- **【所属模块/功能】** 认证 Auth / 数据初始化
- **【缺陷描述】** `DataInitializer` 建的示例用户 openid 是 `mock_openid_user_001`，而 `AuthService` 未配置微信凭据时返回的 openid 固定为 `mock_openid_stable`，两者不一致。结果：微信登录后得到的是全新空账号，seed 中为该用户准备的 3 条示例订单、1 条检测结果、3 条站内消息全部不可见，README 描述的"微信登录 → 看到示例数据 → 医护扫码核销"演示链路无法走通。
- **【复现步骤】**
  1. 启动后端
  2. `POST /api/auth/wechat-login {"code":"任意"}` → 注册 → 登录
  3. `GET /api/orders`
- **【预期结果】** 应命中 `user_id=1`（张阿姨），可见示例订单
- **【实际结果】** 登录后是全新空账号，订单列表为空
- **【严重程度】** 一般
- **【关联代码位置】** `config/DataInitializer.java:37`（`openidPrefix + "user_001"`）vs `service/AuthService.java:150`（`openidPrefix + "stable"`）
